# PARI-GP-ENGINE

Run [PARI/GP](https://pari.math.u-bordeaux.fr/) code inside [Quarto](https://quarto.org)
documents, and have it highlighted properly.

This repository provides two things that fit together but can be used apart:

| | What it is |
|---|---|
| **Engine** | A Quarto [engine extension](https://quarto.org/docs/extensions/engine.html) that executes ` ```{gp} ` cells with the `gp` interpreter and puts the results in the rendered document. |
| **Highlighting** | A KDE/Skylighting syntax definition (`pari-gp.xml`) covering all 1200 functions of PARI/GP 2.17, applied automatically — no `syntax-definitions:` wiring needed. |

```{gp}
p = nextprime(10^30)
factor(p - 1)
```

## Requirements

- **Quarto ≥ 1.9** — engine extensions do not exist in earlier versions.
- **PARI/GP** — the `gp` executable must be on your `PATH` (or named explicitly, see below).

## Installing

```bash
quarto add oeistools/PARI-GP-ENGINE
```

Or clone the repository and run the installer, which checks the prerequisites
first and tells you exactly what is missing:

```bash
./install.sh            # Linux, macOS
./install.ps1           # Windows
./install.sh --check    # report only, install nothing
```

## Using it

Set `engine: pari-gp` in the front matter, then write ` ```{gp} ` cells:

````markdown
---
title: "Mersenne factors"
engine: pari-gp
format: html
---

```{gp}
M = 2^101 - 1
factor(M)
```
````

```bash
quarto render mersenne.qmd
```

### One session per document

Every cell in a document runs in **one** `gp` session, in order, so anything a
cell defines is still there in the next one:

````markdown
```{gp}
E = ellinit([0, -1, 1, -10, -20]);   \\ X_0(11)
```

```{gp}
E.disc
ellak(E, 7)
```
````

This also means gp's own conventions apply as usual: a statement ending in `;`
computes without printing, and one without `;` prints its value.

### Cell options

Written as `#|` comments at the top of a cell.

| Option | Default | Effect |
|---|---|---|
| `eval` | `true` | Run the cell. `false` shows the code without running it. |
| `echo` | `true` | Show the source. |
| `output` | `true` | Show what gp printed. `asis` inserts it as raw markdown instead of a code block. |
| `error` | `false` | `true` renders gp errors into the document; `false` stops the render. |
| `include` | `true` | `false` drops the cell from the output entirely (it still runs). |
| `classes` | — | Extra CSS classes for the code block. |
| `filename` | — | Filename label above the code block. |

````markdown
```{gp}
#| echo: false
#| output: asis
print("## A heading generated by gp")
```
````

### Document options

Everything under `pari-gp:` in the front matter, all optional:

```yaml
---
engine: pari-gp
pari-gp:
  path: gp              # gp executable, if it is not on PATH
  args: []              # extra arguments passed to gp
  stacksize: 32M        # parisize
  primelimit: 500000    # primelimit
  precision: 50         # realprecision, in decimal digits
  bitprecision: 128     # realbitprecision (alternative to precision)
  seriesprecision: 16   # seriesprecision
  timeout: 300          # seconds before the render gives up
  highlight: true       # inject the syntax definition automatically
  prelude: |            # gp code run once, before the first cell
    default(output, 0);
    read("mylib.gp");
  echo: true            # defaults for every cell in the document
  output: true
  error: false
---
```

### Errors

By default a PARI/GP error stops the render and reports the cell and the
message, which is what you want for a document that is supposed to be correct.
When the error *is* the point, ask for it:

````markdown
```{gp}
#| error: true
1/0
```
````

The session survives either way — gp keeps reading, so later cells still run.

Note that gp's `*** Warning:` lines (for instance when the stack has to grow)
are warnings, not errors: they are shown but never stop a render.

## Highlighting on its own

The syntax definition works with plain Pandoc and with Quarto documents that do
not use the engine at all. Tag a block `pari-gp` (or `gp`) and point Quarto at
the file:

````markdown
---
format:
  html:
    syntax-definitions:
      - _extensions/oeistools/pari-gp/pari-gp.xml
---

```pari-gp
forprime(p = 2, 100, print(p))
```
````

It covers comments (`\\ ...` and `/* ... */`), strings, numbers including hex
and floats, gp metacommands (`\p`, `\q`, `?fn`), member access (`E.disc`),
`default()` names, control flow, and every built-in function.

The definition is not written by hand: `tools/gen_xml.py` asks the installed
`gp` for its own function list, so it can be regenerated for a newer PARI/GP:

```bash
make syntax
```

## Development

```bash
make build      # compile src/pari-gp.ts -> _extensions/pari-gp/pari-gp.js
make syntax     # regenerate pari-gp.xml from the installed gp
make test       # render the test documents and check the output
make examples   # render examples/
make check      # all of the above
make doctor     # report whether quarto and gp are usable
```

The engine is written in TypeScript against the types Quarto ships, and
compiled with `quarto call build-ts-extension`. The compiled
`_extensions/pari-gp/pari-gp.js` is committed, because that is the file Quarto
actually loads when someone installs the extension.

### How execution works

Quarto's engine API hands the engine the whole document and takes back
markdown. So the engine collects the code of every cell, joins it into a single
gp script with a sentinel `print()` after each cell, runs that script through
one `gp -q -f` process, and splits the combined output back apart on the
sentinels.

gp's stderr is merged into its stdout **by the shell** rather than by reading
two pipes. That is deliberate: a gp error is reported *between* two results of
the same cell, and only the merge preserves that position. A sentinel after the
start-up code keeps gp's own chatter out of the first cell.

## Limitations

- Quarto allows **one engine per document**, so a document using `pari-gp`
  cannot also run `{python}` or `{r}` cells. This is a Quarto restriction, not
  one of this extension.
- No caching or freeze support yet: every render re-runs the whole document.
- Plotting (`plothraw`, `psploth`, …) is not captured as figures yet.
